# requirement-clarify 设计文档

> 目标：把"需求确认"做成一道硬性关卡——在用户明确确认需求、所有阻塞性问题解答完毕之前，agent 不动手实现。澄清阶段的 agent 只做推导、结构化与提问，不做构建。

## 1. 设计原则

- **确认前置**：实现前必须经过"复述 → 提问 → 用户确认"的完整闭环，杜绝拿到模糊需求就开写的倾向。
- **问题收口**：提问集中在明确的关口（首轮澄清、落实前扫尾）以整轮形式发出，不在实现过程中零碎追问；已回答的问题绝不重复。
- **三态问题管理**：每个问题始终处于且仅处于一种状态——已解答 / 用户显式搁置 / agent 自定默认值待确认；搁置项不追问也不按假设实现，自定默认值必须显式标注并持续可见。
- **证据裁决**：已确认需求稳定但并非不可错——任何证据（测试失败、运行行为、文档、用户反馈、外部数据）与之矛盾时，主动带证据发起再确认，既不沉默服从也不擅自推翻。
- **决策链明确**：落实方式的优先级为——用户当前明确要求 > 用户记忆中的偏好 > agent 提议并经用户点头的默认值。
- **确认结果即事实源**：确认后的需求是后续一切工作的唯一依据；被再确认修订时更新清单条目而非新旧并存；后续改动不得破坏既有已确认行为（回归保护）。
- **增量处理追加需求**：后续需求按"与现有逻辑一致 / 不明确或冲突"二分，前者直接融入，后者只对增量部分走一轮小型澄清，不重复确认已定内容。

## 2. 阶段一：推导与呈现（Infer & Present）

1. **分析请求**：从用户表述中推导其真实期望的需求，覆盖——目标（解决什么问题）、范围（包含什么、明确不包含什么）、预期产出（交付形态、验收标准）、约束（技术栈、环境、兼容性、时间——仅在已声明或明显隐含时列出）。
2. **复述需求**：以"我的理解"形式输出简洁的结构化复述，短到用户可以一眼核对；推断出的假设显式标注。
3. **列出待确认问题**：在复述下方列出所有实质性影响实现的不明确点，编号提问；每个问题必须具体、可决策（范围边界、数据来源、优先级、取舍、边界情况），拒绝空泛套话；**每个问题附建议默认答案**，用户可一句话批量采纳。对可量化的规则，附一个具体示例（输入 → 期望输出）供用户确认；不可量化的需求不强求。
4. **优先内置提问工具**：凡问题需要用户确认时，**优先调用运行环境提供的内置提问工具**（如结构化选择题式的追问工具）而非纯文本提问——它能显式呈现选项、可靠收集决策。将每个问题的建议默认答案映射为工具选项（推荐项排前），并保留自由输入能力，允许用户在给定选项之外作答；仅在无此类工具或问题无法表达为选项时回退到纯文本提问。
5. **停下等待**：不实现、不搭脚手架、不"先写个草稿"，下一步属于用户。

## 3. 阶段二：确认循环（Confirmation Loop）

6. **处理用户回复**：用户可确认、修改、搁置或分批回答，循环可能持续若干轮。
   - 用户修改时：更新复述，**只呈现变化的部分**及修改引发的新问题；用户的修改回答即对应问题的解答，不重复追问。
   - 用户确认时：复述 + 已解答问题共同构成**已确认需求**。
7. **循环直至明确确认**：确认过程较长时，收尾输出一份紧凑的最终确认清单，让双方共享同一版本的事实源。长周期项目可提议将确认清单（连同搁置问题与验证锚点）写入项目内记录文件，供后续会话恢复共享状态。
8. **问题三态跟踪**：每个问题在落定前始终处于且仅处于一种状态：
   - **已解答**：用户已回答——绝不重复追问；
   - **显式搁置**：用户主动选择延后（如"以后再说""等数据"）——记录在案，不得按假设实现，不在后续扫尾中反复追问，但在每次汇报中保持可见，直至用户回头处理；
   - **agent 自定默认值**：无法获得答案——按项目惯例与上下文采用合理默认值，**显式标注"agent 自定、待确认"**，并在每份汇报与最终清单中持续列出，直至用户确认或被证据推翻。
9. **确认结论保持稳定**：后续更改已确认结论须用户显式再确认，静默偏离是红线。再确认修订某结论时，**更新**最终清单中的对应条目（注明修订来源），不保留新旧两版并存。

## 4. 阶段三：落实前扫尾（Pre-implementation Check）

10. **扫尾提问**：确认后检查问题清单中尚未落定的项（用户可能确认了复述却跳过了部分问题）。将真正未回答的问题**合并为一轮**在动手前统一问完（有内置提问工具时同样优先使用）；显式搁置的问题保持搁置状态顺延，不重复追问；agent 自定默认值则再次呈现请用户明确确认。
11. **无残留即声明**：全部落定时简要说明后直接进入落实，不为问而问。

## 5. 阶段四：确定落实方式（Delivery Approach）

12. **确定交付方式**，按优先级：
    - 本次对话中用户的明确要求；
    - 其次是工具提供给模型的用户记忆中的偏好（交付风格、模块组织习惯、验证习惯等）；
    - 都没有时，由 agent 提议合理默认值（如分模块渐进式推进并设检查点、小任务一次性完成），一句话征得用户同意后开始。
13. **按既定方式交付**：渐进式则逐模块完成并在每模块后简要汇报与验证；一次性则整体完成后统一汇报。本次需求内交付方式保持不变，除非用户更改。用户给过具体示例（输入 → 期望输出）时，优先用这些示例核对交付物。

## 6. 阶段五：追加需求（Follow-up Requirements）

14. **增量分析**：用户在实施中或实施后提出新需求时，与既有已确认需求及现状对比，二分处理：
    - **一致部分**：自然衔接现有逻辑——直接融入现有计划/实现，简要说明融入方式；
    - **不明确或冲突部分**：范围含糊，或与已确认结论/现有逻辑冲突——仅对这部分走一轮小型"复述 → 提问 → 等待 → 确认"闭环，确认前不动任何东西。
15. **仅对增量执行后续流程**：追加需求确认后，只对增量部分执行扫尾提问与落实方式确定，不重新确认已定内容。融入完成后**回归验证**既有已确认行为未被破坏（用项目自身的测试/检查手段），并在汇报中给出回归结果。

## 7. 证据纪律（实施中与实施后）

16. **证据优先于确认**：任何证据——测试失败、运行行为、文档、用户反馈、外部数据——与已确认需求矛盾时，停止沉默沿用任何一方：带着证据上报冲突，对受影响部分发起小范围再确认。已确认需求是稳定的，但不是不可错的。
17. **异常上报而非掩盖**：已确认需求若导致明显不合理或自相矛盾的结果，报告异常现象及判断依据，请用户复核原始需求——只呈现观察让用户决策，不默默交付，也不单方面断言需求错误。

## 8. 通用不变量（红线）

- **未经用户明确确认需求，不得开始实现**。
- 每个问题具体、可决策、附建议默认答案；已回答的问题不重复。
- **凡需用户确认的提问，优先使用内置提问工具**；纯文本是回退手段而非默认手段。
- 提问在既定关口整轮发出（首轮澄清、落实前扫尾），不在实现过程中零碎追问。
- 每个问题始终处于且仅处于一种状态——已解答 / 显式搁置 / agent 自定默认值待确认；搁置项记录并持续可见，但不追问也不按假设实现；agent 自定默认值必须显式标注。
- 已确认需求是唯一事实源，偏离须再确认——矛盾证据始终触发再确认，而非沉默服从或擅自推翻。
- 后续改动不得破坏既有已确认行为；汇报回归结果。
- 落实方式始终遵循：用户明确要求 > 记忆中的用户偏好 > 提议并经确认的默认值。

## 9. 落地形态

skill 为纯流程型，不包含 `scripts/`、`references/`、`assets/`：

```
requirement-clarify/
└── SKILL.md        # 通用流程（五阶段 + 证据纪律 + 通用不变量），英文

设计文档（本仓库统一存放）
└── docs/
    └── requirement-clarify.md   # 本文档（中文）
```

- **SKILL.md** 是唯一入口，复制到目标项目（`.agents/skills/`，Claude Code 为 `.claude/skills/`）即可使用，无需修改。
- 本 skill 默认不落盘状态文件，确认结果以对话内最终清单为准；长周期项目可由 agent 提议将确认清单/搁置问题/验证锚点写入项目内记录文件（可选机制）。
- 设计来源注记：问题三态、证据裁决、回归保护、修订更新清单等机制源自一次确定性模拟项目的实践沉淀；该项目特有的验证手段（种子复现、批量统计、赔率校准、逐行日志比对）未纳入 skill，仅吸收其抽象层——可复现的单例验证、回归基线、多数据源交叉裁决。
