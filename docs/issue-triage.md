# issue-triage 设计文档

> 目标：agent 作为**信息枢纽与执行代理**，用户作为**唯一决策者**。接入新项目时将 skill 复制进项目仓库，上下文卡由 agent 检索生成、用户审阅后写入。

## 1. 设计原则

- **决策权分离**：所有价值判断（做不做、算不算 bug、是否违背项目方向）一律留给用户；agent 只补充事实与技术判断，分类结论以"建议"形式呈现。
- **审阅前置**：所有对外可见的写操作（评论、标签、里程碑、关闭、转移、PR）一律先经用户审阅。
- **不预设操作**：执行阶段不预设分支，由用户开放性指定处理方式。
- **可恢复**：进度按 issue 落盘，会话中断后可续跑。

## 2. 第 0 步：项目上下文注入（agent 生成，用户审阅）

上下文卡**由 agent 检索仓库后自动生成草稿**，用户审阅确认后写入 **SKILL.md 同级目录**（`project-context.md`），后续读取也从该位置获取。**推荐将 skill 安装在项目内**（每项目一份），保证上下文卡与项目一一对应。

**生成方式**：agent 通过检索仓库自动填写——README / CONTRIBUTING、目录结构、CI 配置、issue 模板、`gh label list` 等，不以猜测代替事实；无法从仓库推断的字段（如"用户偏好"）标为 `待补充` 并在汇报中列出，通过**询问用户获得后补写**。

上下文卡内容：

- **仓库信息**：`owner/repo`、默认分支、issue 语言习惯（回复用语言）
- **issue 标签列表**：从 `gh label list` 拉取的仓库实际标签清单（含各标签语义说明）。**所有打标操作只能使用此列表中的标签**，不擅自新建；确需新标签时先征得用户同意，创建后同步更新此列表
- **项目规范摘要**：代码结构、关键目录、改动时的强制清单、lint/test 命令
- **变更红线**：哪些文件/行为不能擅动（如配置结构版本、发布流程）
- **提交策略**：改码的交付形式——直接创建提交，还是新建分支并创建 PR（未声明时默认走 PR）
- **收尾策略**：修复后 issue 何时可关（即时 / 等验证 / 等发版），用什么标签标记中间态（中间态标签须存在于标签列表中）
- **用户偏好**：本流程的行为偏好，由询问用户获得并持久化（非仓库检索所得），例如——进度跟踪是否启用、进度目录、其他后续新增的偏好项；后续运行直接按偏好执行，不再重复询问

**缺失处理**：启动时读取 SKILL.md 同级目录，找不到 `project-context.md` 则**询问用户是否创建**；用户同意后走上述"检索生成 → 审阅 → 写入"流程。用户拒绝时采用最保守兜底策略——不自动关闭、不执行任何打标/元操作、所有代码交付一律走 PR（此场景下无提交策略可依，按阶段三默认值处理），并在首次汇报中说明。

## 3. 阶段一：收集与摘要（Fetch & Digest）

1. **拉取列表**：`gh issue list` 按状态/标签/时间过滤，并加 limit 截断（每轮最多处理 10~20 个，按活跃度/时间排序），输出总览表（编号、标题、标签、最后活跃、是否有关联 PR）。
2. **逐项深读**：正文 + 评论，产出固定模板摘要。**限流策略**：单 issue 评论超过 50 条时，只摘取首楼、最新 20 条和高赞评论，避免上下文溢出。摘要模板：
   - 本质诉求（一句话）
   - 关键事实（复现路径、报错、环境、讨论分歧）
   - 关联线索（相关文件、相似 issue、附带 PR）
3. **初步分类建议**：给出 bug / feature / docs / 咨询 / 重复 / wontfix 候选的**推测性分类建议**，供用户复核。对"重复 / wontfix"这类高敏感结论必须附带证据（重复 issue 编号、讨论原文引用），且不自动执行任何关闭动作。同时标出**信息缺口**（需追问的点）。
4. **进度落盘**：首次落盘前**询问用户是否启用进度跟踪**，以及**进度目录**（默认建议当前运行工具的数据子目录下按 skill 名称命名的子文件夹，如 `.codebuddy/issue-triage/`、`.claude/skills/issue-triage/` 等；用户也可自行固定其他路径）。用户确认后将"是否启用 + 存放路径"写入上下文卡**用户偏好**，后续运行直接按偏好执行，不再重复询问；用户未启用则跳过落盘。进度跟踪采用**每个 issue 一个文件**：在进度目录下为每个 issue 创建独立文件（如 `<issue-number>.md`），记录该 issue 的处理阶段（已摘要 / 待决策 / 已执行 / 已收尾）及关键决策摘要；恢复执行时扫描进度目录即可续跑，单个 issue 的进度互不影响。

## 4. 阶段二：决策呈现（Present, Don't Decide）

5. **决策卡片**：呈现事实摘要、初步分类建议、成本预估与信息缺口，供用户参考；**不预设固定选项清单**，由用户开放性决定如何处理（可以只描述意图，不必从列表里挑）。
6. **成本预估**：若改码，列出预计影响面（涉及模块、是否触发项目的强制清单、是否影响兼容性边界），供用户权衡。
7. **硬性原则**：所有价值判断（做不做、算不算 bug、是否违背项目方向）一律留给用户；agent 只补充事实与技术判断，分类结论以"建议"形式呈现，最终由用户确认。

## 5. 阶段三：执行（User-Directed Execute）

8. **开放性询问**：用户对某个 issue 作出决定后，agent 询问"希望如何处理、由谁来执行"，**不预设操作分支**。用户可以自由回答，典型方向包括但不限于：
   - **用户自行修改**：agent 只提供定位与建议（文件、行号、相关代码片段、修改思路），不动代码；
   - **指导 agent 修改**：用户给出方向和约束，agent 负责实施；
   - 其他任何操作（起草回复、追问、打标、关闭等）同样由用户开放性指定，agent 不主动代选。
9. **agent 实施时的约束**（无论用户怎么指定，以下约束始终生效）：
   - **改码**：遵循项目规范完成修改，且**不得触碰上下文卡声明的变更红线** → 跑项目的 lint/test → 展示 diff → 用户确认后按上下文卡**提交策略**交付——创建 PR（正文引用 issue 编号，是否合并由用户决定）或直接创建提交；提交策略未声明时默认走 PR；提交信息按 Conventional Commits 引用 issue 编号；
   - **对外文案（回复 / 追问）**：与 **issue 作者**的语言一致（无法判断时回退到上下文卡声明的 issue 语言习惯）→ 用户审阅 → `gh issue comment` 发布；未审阅不发布；
   - **元操作（打标、改里程碑、关闭、转移）**：打标**只能使用上下文卡标签列表中的标签**，不擅自新建，确需新标签先征得用户同意并同步更新列表；全部属于对外可见的写操作，一律需用户审阅确认后执行，关闭必须附关闭理由。

## 6. 阶段四：收尾与闭环（Close the Loop）

10. **状态策略**：默认不自动关闭。关闭条件按第 0 步注入的收尾策略执行（该字段标 `待补充` 时按默认"不自动关闭"处理，并在汇报中提示用户补全）；待验证的 issue 打中间态标签（如 `pending-feedback`），中间态标签**须存在于标签列表**，缺失时先征得用户同意创建；用户拒绝创建上下文卡的场景下，不执行任何打标。
11. **记录关联**：代码提交、PR、评论、标签变更都保留 issue 编号引用，保证 changelog 工具（git-cliff 等）能自动归组。
12. **循环**：更新对应 issue 的进度文件（若已启用）→ 回到阶段一处理下一个 issue，直至本轮队列清空。会话中断后恢复时先扫描进度目录读取各 issue 进度，跳过已完成阶段。

## 7. 通用不变量（任何项目都适用的红线）

- **所有对外可见的写操作**（评论、标签、里程碑、关闭、转移、PR）**一律先经用户审阅**
- 改码必须通过项目自身的检查命令后才可提交，交付形式（提交 / PR）按上下文卡提交策略执行，未声明时默认走 PR
- 每轮操作结束后按固定模板汇报：
  1. 本轮处理数
  2. 各 issue 当前状态表
  3. 待用户处理清单
  4. 下一轮建议

## 8. 落地形态

skill **安装在项目内**（每项目一份，上下文卡与项目天然一一对应）：

```
项目仓库内/
└── issue-triage/
    ├── SKILL.md                                  # 通用流程（第 0 步 + 四阶段 + 不变量），英文
    └── references/
        └── project-context-template.md           # 上下文卡模板（生成 project-context.md 的依据）

设计文档（本仓库统一存放）
└── docs/
    └── issue-triage.md                           # 本文档（中文）
```

- **SKILL.md** 是稳定层，接入新项目时整体复制到该项目仓库即可，不需修改；启动时由 agent 检索当前仓库生成上下文卡草稿 → 用户审阅 → 写入 SKILL.md 同级目录，后续每次运行从这里读取。
- **project-context.md** 不随 skill 复制，而是运行时生成；进度文件按 issue 一份，存放在用户偏好指定的进度目录。
- **设计文档**统一存放在本仓库顶层 `docs/` 目录（文件名用 skill 名），不随 skill 复制分发。
